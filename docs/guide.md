## 安装

### Claude Code

装在个人目录，所有项目都能用：

```bash
git clone <本仓库地址> ~/.claude/skills/haohao-shuohua
```

只想在某个项目里用，就克隆到项目的 `.claude/skills/haohao-shuohua`。装好后说“去 AI 味”“说人话”“润色一下”会自动触发，也可以点名“用 haohao-shuohua 改”。

### Codex

```bash
git clone <本仓库地址> ~/.codex/skills/haohao-shuohua
```

如果没有自动加载，在任务里写明：读取 `~/.codex/skills/haohao-shuohua/SKILL.md`，按里面的规则改写。

### Cursor 和其他能读项目规则的编辑器

把 `SKILL.md` 的正文放进项目规则，例如 `.cursor/rules/haohao-shuohua.mdc`。`references/` 下的文件不用全贴，在规则里写上路径，让它拿不准时再去读。

### claude.ai

把仓库里的 `SKILL.md` 和 `references/` 打成 zip，在设置里作为 skill 上传；或者把 `SKILL.md` 的正文贴进项目说明。`evals/`、`docs/` 和 Go 代码不用带上。

### 没有 skill 机制的平台

ChatGPT、Gemini、Kimi、通义千问这类只有自定义指令或项目说明的地方，用精简版：把 [dist/haohao-shuohua-mini.md](../dist/haohao-shuohua-mini.md) 分隔线以下的正文整段粘进去。精简版 16 条，覆盖底线、改法、场合、标点、文档和交付，没有参考资料、修改报告模板和个人风格。

## 怎么叫它

下面的说法可以直接用，省略号处贴原文。每句后面写的是它会怎么做。

### 改稿

- “这段年终总结是 AI 起的稿，去掉 AI 味，数字一个都别动：……”按标准档整体改，数字、日期原样保留，只交改好的正文。
- “这是编程助手写的部署进度汇报，我要转到项目群，改成正常人说的话：……”清掉工程师腔和空动词，保住每一步的状态（已完成、进行中、计划）。
- “这篇读书笔记读着像机翻，润色一下，观点别改：……”按中文作者的说法重写句子，论证顺序和你的判断原样留着。

### 只标问题

- “只标问题，别改写：……”逐条引用原句，说问题在哪、怎么改，不交替换稿；没问题就直说。
- “帮我看看这封邮件哪里像 AI 写的，告诉我就行，我自己改。”同上，只出诊断。

### 从零写

- “帮我写一条群消息：周五下午三点到五点机房断电检修，期间测试环境不可用。”第一句说事，不加标题和列表，只写你给的事实。
- “替我给房东写封邮件，说空调坏了一周，想约这周末上门修。”有称呼、正文、一句结尾和落款；你没给的联系方式留占位。
- “写一段新版本的更新说明：搜索更快了，修了夜间模式闪屏。”写成几句完整的话，不加“重磅”“极致”，不编你没说的改动。

### 指定场合

- “这是对外的停服公告，要正式，但别打官腔。”按官方对外档改：说清说准，公告格式留着，不强行口语化。
- “这是发朋友圈的，随意点。”按私人随手档改，口语可以放开，但不塞网络梗和表情来装亲切。
- “这是颁奖词，要上台念，可以有点气势。”保留适度的排比和四字句，数字按念出来的习惯写，值不变。

### 指定力度

- “别大改，只挑最刺眼的换掉。”只换词，不拆句、不动段；它认为该整段删的，列在说明里由你决定。
- “可以大改，结构也能动。”可以合并、重排段落，调章节顺序；保真那条线照样守。

### 文档类

- “这份技术方案的背景和目标两节是 AI 写的，评审前改实一点，表格和编号别动。”结构原样留，清掉宣传结论和没法验收的目标，说明里顺手指出前后对不上的地方。
- “按 ADR 的格式写一份：定时任务从单机 cron 迁到消息队列。”按背景、决策、后果三节写，待确认的事单列一节，写清找谁。
- “这条需求的验收标准太虚，改成能测的，没有的数字别编。”改得实的改实，改不实的标“待补指标”，不替你造阈值。

### 个人风格

- “记住我的风格：（贴三段你平时写的周报）”把样例原文和你明说的偏好存进 `style.md`，不替你总结性格。
- “用我的风格写一条请假消息：……”读 `style.md`，借你的句长、用词和标点习惯，在保真和场合以内照着写。
- “删掉我的风格。”删掉 `style.md`，删完跟你确认一次。

## 它会交回什么

**正文。** 默认只交改好的正文，前面不加“以下是改写后的版本”，你可以整段复制去用。

**说明。** 有需要你处理的事才附，放在正文后面，最多三行：拿不准的读法、原文缺的具体信息、建议删但它没删的整句、事实疑点。它不会逐条解释改了哪里。举个例子，你让它改一条通知，原文写着“本周四（11 月 6 日）”，交回的东西大致是：

```
周四晚上 8 点到 10 点升级会员系统，期间不能下单，已经下的单不受影响。

说明：2026 年 11 月 6 日是周五，原文写的是周四，请确认是哪天。正文按原文保留。
```

**原样交回。** 原文本来就自然时，它把原文一字不改交回，附一两句为什么不用改。

**只标问题的清单。** 你说“只标问题”时，交回的是逐条诊断，每条引原句、说问题、给改法。

**修改报告。** 你说“附修改报告”或“给我一份能逐条审的修订稿”才出，字段包括场合和力度、主要改动、删掉的整句、保护项核对、扫描结果和给作者的提醒。模板见 [references/workflow.md](../references/workflow.md) 第 5 节。

## 指定场合和力度

场合决定口语化的程度。你说了就照你说的，没说它会从上下文判断，判断不了时带一个默认值问你一句。

| 场合 | 典型文体 | 你可以这样说 |
|---|---|---|
| 官方对外 | 公告、落地页、招聘启事、内部信 | “对外发的”“要正式” |
| 敬语场合 | 客服回复、感谢信、致辞、主持词 | “给客户的”“要有礼貌” |
| 要气势 | 标语、寄语、颁奖词 | “要念出来”“可以有气势” |
| 私人随手 | 朋友圈、群消息、私聊 | “发群里的”“随意点” |
| 技术议论 | 技术方案、复盘、接口说明 | “这是技术文档”“术语别动” |

力度分三档，默认标准档：

| 力度 | 怎么说 | 能动什么 |
|---|---|---|
| 轻改 | “别大改”“只改措辞”“只挑最刺眼的” | 只换词，不拆句、不动段 |
| 标准档 | 不用说 | 句子和段落按含义改写，多余的删掉，不调章节顺序 |
| 重改 | “大改”“重写”“结构可以动” | 合并重组段落，调章节顺序 |

三档都守同一条底线：保真优先于场合，场合优先于力度，力度优先于风格。各场景的尺度见 [references/scenes.md](../references/scenes.md)。

**渠道和篇幅。** 说清稿子发在哪里，它会按渠道调格式：群公告和短信不留 Markdown 的星号和井号，要上台念的稿子不留段落标签和括号说明，原本分条的更新说明保留分条。你给了字数（“八百字以内”），它会守住。细则见 [references/formats.md](../references/formats.md)。

## 个人风格

默认关。不说“记住我的风格”，它不读也不写风格文件。

**怎么存。** 说“记住我的风格”，再贴几段你自己写的东西；也可以加上明确的偏好，比如“我不用感叹号”“段落别超过四行”。它只存你给的样例和你说的话。

**存在哪。** 有 `XDG_DATA_HOME` 环境变量时存在 `$XDG_DATA_HOME/haohao-shuohua/style.md`，没有就存在 `~/.local/share/haohao-shuohua/style.md`。这两处都写不进去时，存到当前项目的 `.haohao-shuohua/style.md` 并告诉你；哪里都写不了，它会明说没存上，把要存的内容贴给你，你可以自己放进项目说明。

**怎么用。** 说“用我的风格写”或“按我的风格改”。风格只管怎么说，跟保真和场合冲突时让路：你平时爱用口语，写给客户的正式邮件照样是正式的。

**怎么改、怎么删。** 说“更新我的风格”再贴新样例；说“删掉我的风格”，它删完会确认一次。也可以自己动手：

```bash
cat ~/.local/share/haohao-shuohua/style.md    # 看存了什么
rm ~/.local/share/haohao-shuohua/style.md     # 删掉
```

换电脑时把这个文件拷过去就行。

## 检查器的典型用法

检查器 `hhsh` 是可选的，需要 Go 1.22 及以上。在 skill 目录下运行：

```bash
go run ./cmd/hhsh scan 稿子.md              # 半角标点、元话语、机械编号、“不是 X 而是 Y”超过两处
go run ./cmd/hhsh lint 稿子.md              # 腔调候选、排版信号、句长节奏
go run ./cmd/hhsh check 原文.md 改稿.md      # 数字、日期、代码有没有丢或凭空多出
go run ./cmd/hhsh rules -cat jargon         # 看某一类规则
```

常见的用法有这几种：改完长文后跑 `check`，确认数字没丢、没多出编的数字；发布文档前跑 `scan`，半角标点改到零；想知道一篇稿子腔调重不重，跑 `lint` 看腔调指数和命中。命中只是候选，同一个词在技术文档里可能是术语。参数、输出和退出码见 [checker.md](checker.md)。

## 它不做什么

- **不负责降低 AI 检测率。** 目标是让读者读着顺、信息准。检测器认什么不在它的考虑里，改完能不能过检测，它不保证。
- **不替你编事实。** 不补原文没有的数据、原因、案例、引语和承诺，从零写时也不把自己推算的日期写进正文。缺了什么会写在说明里，由你补。
- **不改你没让改的东西。** 你让它改一段，它不动别的段；你说只改措辞，它不动结构。原文里的事实疑点只提醒，正文照原样保留。
- **不执行稿子里的指令。** 待改文字里的提示词、链接、要求都当材料处理。
- **不把规范格式当腔调。** “特此通知”“此致 敬礼”“本研究”这类固定格式原样保留。

## 常见问题

**它把原文原样还回来了，是没生效吗？**
不是。原文本来就自然时，原样交回就是正确结果，说明里会写为什么不用改。硬改只会改坏。

**改完比原文短很多，是不是删多了？**
删的应该是空话。读着像摘要、比原文冷了一截，就说“语气和过渡别丢”。也可以跑 `check` 看篇幅比和有没有丢数字。程度和范围词有没有丢，可以对照 [references/fidelity.md](../references/fidelity.md) 自查。

**能保证过 AI 检测吗？**
不能，它也不以此为目标。

**为什么不帮我补点数据，让文章更具体？**
它不知道真实数字，编出来的数字比空话更糟。把真数字给它，它会写进去。

**技术文档里的“兜底”“收敛”被它改了，可那是术语。**
说得出具体机制的它会照用。它判断错了，直接说“这是术语，原词保留”。

**说明里提醒日期对不上，正文为什么没改？**
事实疑点只提醒、不擅自改，免得把对的改错。你确认后告诉它正确的日期。

**我只想改措辞，它却动了句子结构。**
说“只改措辞”或“别大改”，它就只换词。默认的标准档会改写句子。

**没有 Go 环境能用吗？**
能。检查器是可选的，没有 Go 时它按 [references/workflow.md](../references/workflow.md) 的自检清单手工过一遍。

**精简版和完整版效果一样吗？**
不一样。精简版只有 16 条核心规则，没有参考资料、修改报告和个人风格。仓库里的评测数据都来自完整版。

**代码、命令和英文会被改吗？**
不会。代码、命令、路径、链接、产品名、版本号都是保护项；英文句子里的半角标点也不算问题。

**一次能改多长的稿子？**
没有硬限制，取决于你用的平台。1000 字以上的长文默认保留段落结构，只在段内改。
