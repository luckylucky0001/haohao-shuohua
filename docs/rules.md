# 规则为什么这样定

SKILL.md 只写“怎么做”，这里写“为什么”：每条主要规则从哪来、解决什么问题、有什么证据、有什么代价。改规则之前先读这里，免得把验证过的东西改掉。

证据里的“第 N 轮”“D/H 轮”指 [evals/](../evals/) 下的盲评，过程见 [iterations.md](iterations.md)。

## 1. 总的取舍

**保真排第一。** 去 AI 味的工具最常见的失败不是改得不够自然，是改丢了事实、改强了语气。不装 skill 时，72 题里 22–28 题有保真问题（丢信息、加料、改强弱），装了以后降到 4–8 题，而且没有判失败的。自然度上的收益比这个小。所以冲突时的让路顺序是保真 > 场合 > 力度 > 风格。

**SKILL.md 短一点，参考资料长一点。** SKILL.md 每次都会整篇读进去，参考资料按需读。第九、十轮的经验是：把 SKILL.md 整篇重写得更全、更有条理，改稿质量反而下降（第十轮 v0.6.1 对 v0.5.1 逐题 16 比 28）。判官的意见是改完残留更多、语序别扭、说明变长。规则一多，模型在每句话上分配的注意力就少。所以 SKILL.md 只留每次都要用的判断，细则、词表、示范放进 references/。

**规则要有失误做证据。** 每加一条规则，都要能指出评测里哪类输出出了这个问题。凭感觉加的规则，常常把本来没问题的地方改坏。

## 2. 保真类

| 规则 | 解决什么 | 证据 |
|---|---|---|
| 情态词逐个对上（计划、预计、力争、可能） | 把“预计”改成“将”，把“力争”改成“确保” | 第一轮起就是不装 skill 最常见的保真问题 |
| 否定不扩大 | “不是网络的问题”被写成“网络完全正常” | 第二轮起的核对项，针对否定范围漂移 |
| 不补原文没有的原因、例子、承诺 | 改写时顺手“解释”一句，听着合理但原文没有 | 第一轮里不装 skill 最常见的问题：补排障细节、替作者加承诺 |
| 程度和范围修饰不丢 | “整整”“普遍”“初步”这类小词在顺句子时被删 | 第九到十二轮，skill 版本剩下的保真问题一半属于这类 |
| 效果不说满也不说弱 | “打基础”写成“准备好了”，“证实”写成“提示” | 第十一、十二轮的小偏差 |
| 原句有几种读法时不猜 | 主语不明、指代不清时替作者选了一种 | 选错一种就是失真，保守改的代价只是少顺一点 |
| 从零写时用户给的每条事实都落到正文 | 漏写版本号、年份，或编出“我这才知道” | 第九到十二轮从零写题的小偏差 |

代价：保真规则会让改写偏保守，偶尔留下不够顺的句子。这是有意的取舍。

## 3. 场合和力度类

**场合五档。** 去 AI 味不等于越口语越好。公告、致辞、客服回复里的敬语和气势是这个文体的功能件；不分场合一律口语化，判官会判“语体漂移”。

**力度三档，默认标准档。** 用户说“别大改”时只换词，说“重写”时可以调段落。默认标准档是两头的折中：改得太轻，腔调清一半留一半；改得太重，本来就自然的文字会被改坏。第七轮里 v0.4.2 两次采样都把 14 条对照题原样交回，v0.1 第二次采样在新对照题上平均改动了 37% 的字。

**本来就自然的文字原样交回。** 72 题里有 14 条对照题，理想结果是一字不改。早期版本会“顺手润色”，把干练的短句改长。这条规则让对照题的过度修改分降到 0。

## 4. 结构和句式类

**从大到小改。** 先结构、再句子、再词、最后标点。结构理顺了，很多啰嗦的句子自然没了；反过来逐句抠，常常抠出一篇更别扭的稿子。

**“不是 X 而是 Y”全文最多两处。** 这个句式本身没错，错在密度。AI 稿里它和变体（“看似……实则……”“真正……的是……”）常常一段一个。限量比禁用好：有意的对比可以留。

**结构排比用“盖住并列项”判。** 量词标题、凑三的名词串、分号串三连，盖住其中一项看理解会不会少；不会少，说明它在凑数。

**车轱辘话用“并句”判。** 相邻几句并成一句信息没少，就并掉。这个判据比“删重复”好用，因为 AI 的重复常常换了说法。

## 5. 词和标点类

**黑话换成具体的话，只用原文给的信息。** 不知道“赋能”具体指什么，就删修饰、留事实，别编一个具体场景。这条是保真和去味的交叉点。

**术语用原词。** 幂等、回滚、灰度在本行有确切定义，通俗化会改变意思。“兜底”“口径”“收敛”在技术文档里说得出机制就是术语，在聊天和汇报里只是装饰。D1、D2 轮专门测过这条。

**中文里的半角标点清零。** 这是能机械判断的少数几项之一，检查器 `hhsh scan` 直接扫。

**元话语删掉。** “值得注意的是”“不难看出”不带信息，只表示“我要说重要的话了”。

## 6. 交付类

**只交正文，说明最多三行，只写作者要处理的事。** 第十一轮判官意见最集中的一点是说明太长、逐条解释改了哪里。v0.6.3 收紧这条后，文档留出题 12 题里 8 题排在上一版前面。

**双向对账。** 原文到改写查丢，改写到原文查加。只查一个方向，加料就漏掉了。

**查换壳。** 删掉的套话换个说法回来，判官一眼能认出。评价和批评换壳时最容易被磨圆。

## 7. 文档类

PRD、技术方案的结构（编号、表格、代码块）是内容，不是排版过度。v0.4.2 不分体裁地“去格式”，把文档拍成段落；v0.5 加了文档一节，26 题迭代集胜率从 28%–31% 升到 75%–80%，留出题从 47% 升到 67%–81%。

需求强度、指标边界、TBD、非目标是文档的保真重点；宣传结论、排比口号、没法验收的目标照样清。列出具体环节、步骤、范围的句子再啰嗦也只改不删（H3 有一题因为删了这种句子被扣分）。

## 8. 试过但没留下的做法

- **整篇重写 SKILL.md。** 第九、十轮的 v0.6、v0.6.1，规则更全、结构更清楚，改稿反而退步。后来改成以验证过的正文为底，逐条并入新规则。
- **一套标准同时管改稿和从零写。** 第三轮里“删空话”“查加料”被模型套到了自己写的东西上，写出的邮件和更新说明被评“偏冷”“像清单”。后来在“从零写”一节写明：约束的是事实，不是温度。
- **长禁词表进 SKILL.md。** 见词就换只会换出同义腔调，所以词表留在检查器里做提示，SKILL.md 只讲判断方法。
- **默认附修改说明。** 说明一长，判官普遍扣分（第十一轮）。现在修改报告只在用户要的时候给，模板在 workflow.md。
- **自动替换。** 检查器只报候选，不自动改。同一个词在技术文档里是术语，在宣传稿里才是腔调，机械替换会改坏。
