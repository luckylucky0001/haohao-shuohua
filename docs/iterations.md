## 结论

- 用 72 题、每个版本两次采样再测一遍：装 skill 明显好过不装（胜率 54%–61% 对 18%，保真问题从四成降到一成以下，p < 0.001）。
- v0.4.2 和 v0.1 整体打平；v0.4.2 在“本来就自然的文字”上更稳（原样交回，不乱改），v0.1 在改稿题上略好但没有超出噪声。默认交 v0.4.2，v0.1 保留在 git 标签 `v0.1`。
- 再往下分高下，规则已经不是瓶颈：要么扩到几百题，要么请人工评审，比继续加规则有用。

## 文档类专项（PRD、技术方案）

用户要求专门针对 PRD 和技术方案再评测迭代几轮。做法：先写一套文档类用例并冻结，跑出失败模式，改 skill；再用一套没参与迭代的新题做留出验证，同时在 72 条通用用例上做回归，确认文档规则没有伤到别的体裁。

**用例**：`evals/cases-doc/` 26 条（P01–P16 改稿：PRD 的背景目标、用户故事和验收、需求表、非目标与风险、竞品、埋点口径、一页 PRD，技术方案的背景目标、方案对比、接口与数据模型、容量评估、灰度回滚、风险与待定、数据迁移、评审摘要、测试方案、评审意见回复；PN01–PN04 写得好的对照；PW01–PW06 从零写）。`evals/cases-doc-holdout/` 12 条留出题（H01–H12，题材和迭代用的 26 条不重合，写题的子代理没看过 skill 和迭代用例）。两套都在跑分前提交。
