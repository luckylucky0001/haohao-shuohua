### 3. 方案对比与选型

随着电商业务的蓬勃发展，交易体验已经成为平台的生命线，而超时关单正是保障交易体验的关键一环。现有方案为每分钟扫一次 `order_main` 表（`status = 0` 待支付且 `create_time` 早于 30 分钟前）。在日订单约 200 万的体量下，扫表 SQL 的 P99 已达到 1.8 秒，关单最长延迟约 2 分钟，已经难以为交易体验全面兜底。

为推动方案快速收敛，我们从多维度对三种方案进行了全方位深度剖析：

| 维度 | A：Redis ZSet | B：RocketMQ 延时消息 | C：进程内时间轮 |
|---|---|---|---|
| 精度 | 秒级 | 秒级（现有 5.1 集群支持任意时长延时） | 毫秒级 |
| 可靠性 | AOF everysec，宕机可能丢最近 1 秒的任务 | 消息落盘，有重投 | 进程重启任务丢失，需自建持久化 |
| 运维依赖 | 复用现有 Redis 集群，需写轮询消费者 | 复用现有 RocketMQ 集群 | 无外部依赖 |
| 开发量 | 约 5 人日 | 约 3 人日 | 约 8 人日（含持久化） |

不难看出，**方案 B 不仅开发量最小，更在可靠性上具备压倒性优势，是当之无愧的最优解。**

**取舍说明：**

1. 我们放弃了 C 的毫秒级精度。关单场景下秒级精度已完全足够，没必要为此额外承担持久化的开发成本。
2. B 依赖 MQ 集群的可用性。为此，我们保留现有扫表任务作为兜底，频率从每分钟一次降为每 10 分钟一次，以确保 MQ 异常时订单依然能被关闭。
3. 方案 A 存在丢任务的风险，并且仍需编写轮询逻辑，开发量反而高于 B，故不予采纳。

值得注意的是，消费端关单逻辑必须保证幂等，采用条件更新实现：

```sql
UPDATE order_main SET status = 4 WHERE order_id = ? AND status = 0;
```

影响行数为 0 时视为已处理，直接确认消息。

综上所述，通过“延时消息 + 扫表兜底”的组合拳，我们将真正做到全链路兜底无死角，为业务腾飞保驾护航。
