## 4. 功能需求与优先级

为全面提升举报处理效率、打造安全健康的社区生态，本期举报处理后台将围绕“受理—分派—处置—回访”四大环节打造全链路闭环，具体需求如下：

| 编号 | 功能模块 | 需求描述 | 优先级 |
|---|---|---|---|
| F1 | 举报工单队列 | 深度融合多维度信息，按举报类型（`spam` / `porn` / `abuse` / `ip_infringe` / `other`）分队列展示，支持按被举报次数、首次举报时间排序 | P0 |
| F2 | 自动分派 | 智能赋能审核员，按队列轮询分派，单人同时持有的待处理工单不超过 20 张 | P0 |
| F3 | 处置操作 | 支持删除内容、折叠、限流、禁言 1/3/7 天；封号必须二次确认，且仅 L2 及以上审核员可操作 | P0 |
| F4 | 批量处置 | 同一被举报内容的多张工单合并处理，一次处置全部关闭 | P1 |
| F5 | 结果通知 | 处置后通过站内信通知举报人处理结果，文案沿用现有模板 `report_result_v2` | P1 |
| F6 | 处置申诉 | 被处置用户可发起申诉，进入独立的申诉队列 | P2，二期再评估 |
| — | 机审预标注 | 不在本期范围 | 不做 |

> **值得注意的是**，F3 中的“限流”指降低该内容的推荐分发权重，并非接口层面的限流。

## 5. 验收标准

为确保功能高质量交付，真正实现用户体验的显著提升，各项需求的验收标准如下：

- **F1**：举报提交后 ≤ 1 分钟出现在对应队列；在 5,000 条待处理工单的情况下，队列列表页 P95 加载时间 < 2 秒。
- **F2**：任一审核员持有的待处理工单数不超过 20 张；审核员状态切为“离开”超过 10 分钟，其未处理工单自动回收到队列。
- **F3**：每次处置必须写入操作日志表 `moderation_action_log`，记录操作人、操作类型、原因码、时间；L1 审核员调用封号接口 `POST /api/moderation/ban` 应返回 `403 PERMISSION_DENIED`。
- **F4**：合并处理后，该被举报内容下所有工单状态一致变为 `closed`。
- **F5**：站内信应在处置后 5 分钟内送达；发送失败的进入重试，最多 3 次。

综上所述，以上需求与验收标准将全方位保障举报处理后台的高质量上线，助力社区生态健康发展。
