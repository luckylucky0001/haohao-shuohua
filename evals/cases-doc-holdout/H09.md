# RFC-0042：Tern 框架 Timeout Budget 传递

## 1. Motivation

在微服务架构日益复杂的今天，timeout 治理早已不仅仅是一个配置问题，而是关乎整个系统 resilience 的核心命题。当前 Tern 框架的 timeout 是 per-hop 独立配置的，上下游之间没有任何 deadline 信息的传递，这一现状严重制约了系统的稳定性。

一个典型的 case：`order-api` → `order-query` → `inventory-svc`。`order-api` 对 `order-query` 设置的 timeout 是 800ms，而 `order-query` 调用 `inventory-svc` 的 timeout 是 1s，并且配置了 retry 2 次。当 `inventory-svc` 变慢时，`order-api` 在 800ms 时就已经放弃并向用户返回 error，但 `order-query` 仍在继续等待和 retry，最长会占用约 3s 的 goroutine 和连接。

我们在 Trace 平台对该链路做了 3 天的采样：`inventory-svc` 收到的请求中，约 18% 在完成时上游已经 timeout（即 orphan request）。这部分 work 完全是浪费，并且在下游抖动时会进一步放大负载，形成 retry storm。

因此，我们亟需一套端到端的 timeout budget 机制，打通全链路的超时治理闭环。

## 2. Proposal

**核心思路：把剩余 budget 随请求向下传递，每一跳用 min(本地配置 timeout, 剩余 budget) 作为实际 timeout。**

### 2.1 传递格式

在 request metadata 中新增 header `x-tern-budget-ms`，值为发起该跳调用时**剩余的毫秒数**（relative），而不是绝对的 deadline 时间戳。之所以选择 relative 而非 absolute deadline，是因为机房之间的 clock skew 我们无法保证在 10ms 以内，使用 absolute 时间会导致误判。

### 2.2 计算规则

```go
remaining := budgetFromHeader - elapsedSinceRecv - networkReserve // networkReserve 默认 5ms
effective := min(localTimeout, remaining)
if effective <= 0 {
    return ErrDeadlineExceeded // 错误码 1504，不再发起下游调用
}
```

- 没有 `x-tern-budget-ms` header 的请求（比如来自老版本 client），行为与现在保持一致，只使用本地 timeout；
- retry 之前必须重新检查剩余 budget，budget 不足时直接放弃 retry。

### 2.3 Rollout

- v1.8.0 加入该能力，默认关闭，通过 `tern.timeout.propagate=true` 开启；
- 先在 `order-*` 相关服务上 canary 两周；
- v2.0 是否改为默认开启，TBD，取决于 canary 数据。

### 2.4 Non-goals

- 本期只做 Go SDK，Java SDK 的支持待和 Java SDK owner 对齐，本 RFC 不覆盖；
- 不处理 MQ 等异步调用链路的 budget 传递。

综上，该方案将全面赋能 Tern 生态，助力打造高可用、高韧性的服务治理体系。
