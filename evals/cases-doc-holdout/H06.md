request: 下面是昨天离线包更新那个会的语音转写，乱是乱了点，帮我起草技术方案的“背景 / 目标 / 非目标 / 待确认”四节，用小标题分开，别加转写里没有的东西。转写——“嗯……先说现状哈，现在离线地图是按城市下的，更新的时候是整包替换，一个城市包平均下来 180 兆左右吧，北京上海那种大的 400 多兆。然后用户那边，应用商店近三个月的差评里提到离线包的有 214 条，我们人工过了一遍，大概一半是说更新太费流量。对，数据这边现在是每月发一次版。所以这期想做增量更新，就是差分包，先按瓦片也就是 tile 级别做 diff。目标的话，单次更新的流量平均要降到全量的 20% 以内。还有一个硬要求，更新失败必须能回退到旧包，绝对不能出现用户打开地图一片空白。（小周）补一句，只在 Wi-Fi 下自动更新，这个保持现在的逻辑不动。范围上这期只做底图和 POI，路网，就是算路用的 routing 数据，还是走全量，不做增量；按区县下载那种更小粒度的也不做；鸿蒙版这期先不管。还没定的有几个，差分是服务端预生成还是请求的时候现算，存储成本得算一下，我跟数据平台组的老赵约了下周聊；服务端保留最近几个版本的 diff，我说三个，但还没定；落后太多个版本就直接下全量，这个阈值也没定。排期等这几个定了再说。”
must_keep:
  - 现状：离线地图按城市下载，更新时整包替换
  - 城市包平均约 180MB，北京、上海这类大城市 400 多 MB
  - 应用商店近三个月差评中提到离线包的有 214 条，人工过了一遍，约一半说更新太费流量
  - 地图数据每月发一次版
  - 本期做增量更新（差分包），先按瓦片（tile）级别做 diff
  - 目标一：单次更新流量平均降到全量的 20% 以内
  - 目标二（硬要求）：更新失败必须能回退到旧包，不能出现打开地图一片空白
  - 只在 Wi-Fi 下自动更新，保持现有逻辑不变
  - 本期只做底图和 POI 的增量
  - 非目标：路网 / routing 数据仍走全量，不做增量；不做按区县的更小粒度下载；鸿蒙版本期不覆盖
  - 待确认：差分由服务端预生成还是请求时现算，需要算存储成本，下周和数据平台组老赵讨论
  - 待确认：服务端保留最近几个版本的 diff，提议 3 个，未定
  - 待确认：落后超过多少个版本直接下载全量，阈值未定
  - 排期等上述事项确定后再定
targets:
  - 不要“在移动出行日益普及的今天”“离线地图是用户出行的刚需”式铺垫开场
  - 不要“打造极致的离线体验”“全面提升用户满意度”“赋能”“闭环”“全链路”之类空洞目标和套话
  - 不要每节结尾加总结升华，不要“综上所述”
  - 不要把转写里的口语（“哈”“对”“我说三个”）原样搬进方案
traps:
  - 不能编造转写里没有的数据：差评率、日活、下载量、目标完成时间、存储成本数字、各城市包的具体大小
  - 不能编造排期、上线日期、负责人分工（转写只提到小周补充了 Wi-Fi 的事、老赵是下周讨论对象，没说谁负责什么）
  - “大概一半”是对 214 条差评的人工统计，不能写成“50% 的用户”或“半数差评用户”；214 条的基数是“提到离线包的差评”
  - “约 180MB”“400 多 MB”“20% 以内”“近三个月”的模糊边界保留，不能写成精确值
  - 保留 3 个版本只是提议、未定，不能写成“服务端保留最近 3 个版本”
  - 预生成 vs 现算、全量回退阈值都必须放在“待确认”，不能在“目标”里替它做决定
  - 非目标三条（routing 全量、不做区县粒度、鸿蒙不覆盖）不能删，也不能写成“后续迭代支持”
  - 回退要求是“必须”，强度不能弱化成“尽量”“建议”
  - 术语保留：增量更新、差分包、瓦片 / tile、diff、POI、routing、全量、Wi-Fi
  - 应有结构：四个小标题（背景 / 目标 / 非目标 / 待确认），目标和待确认适合用列表；不要擅自加“方案设计”“排期”“风险”等其他章节
