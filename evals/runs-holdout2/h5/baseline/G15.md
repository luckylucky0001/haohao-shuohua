# ADR-017:订单号生成改用号段模式

- 状态:已接受(2026-10-12 架构评审通过)
- 决策人:交易中台 · 孟昭(owner),评审:陆一帆、韩青

## 背景
当前订单号由 MySQL `order_seq` 表自增生成,每次下单都要访问一次主库,这在大促场景下是**主库取号瓶颈**:双十一当天该表 QPS 峰值 4.2 万,主库 CPU 一度到 92%。同时,订单号是连续自增的,竞争对手可以通过两次下单推算出我们的日单量,存在**信息泄露风险**。

## 决策
我们决定采用号段模式,包含三项设计:**“预分配 + 双缓冲 + 随机步进”**。

1. **预分配**:每个应用实例一次从 DB 领取 1000 个号(`segment.step=1000`);
2. **双缓冲**:当前号段消耗到 80% 时(即剩余 20%),异步预加载下一个号段,避免取号阻塞;
3. **随机步进**:号段内相邻订单号之间加 1~9 的随机增量,订单号不再连续。

订单号格式保持 19 位纯数字不变,下游对账、客服系统无需改动。

## 被否决的方案
- **雪花算法**:依赖机器时钟,发生时钟回拨时可能产生重复号。我们的容器经常漂移、NTP 不可控,风险不可接受。
- **UUID**:不是数字,长度 36 位,和 19 位纯数字的格式约束冲突,下游改造面太大。

## 后果
正面:主库取号压力预计大幅下降(粗算约为原来的 1/200);订单号不再可被推算。

负面:
- 应用重启会丢弃号段中未用完的号,订单号会出现空洞,**财务侧需接受订单号不连续**(已与财务的周岚确认可以接受);
- 随机步进会让号段实际可用数量下降到约 1/5,需要把 `segment.step` 调大,具体值待压测后定。
