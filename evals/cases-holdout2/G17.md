## 发票开具结果回调(Webhook)

在数字化转型的浪潮中,发票不仅是一张凭证,更是企业财务流转的“神经末梢”。为了让您第一时间感知开票结果,我们贴心地为您提供了异步回调能力,真正实现开票状态的实时触达与无缝衔接。

### 触发时机
当发票状态变为 `ISSUED`(开具成功)、`FAILED`(开具失败)或 `RED_FLUSHED`(已红冲)时,平台会向您在控制台配置的回调地址发送 `POST` 请求。不难看出,`PROCESSING` 等中间状态不会被推送。

### 请求体示例

```json
{
  "event_id": "evt_20261020_8f3a1c",
  "event_type": "invoice.issued",
  "invoice_no": "INV202610200001",
  "status": "ISSUED",
  "amount": "1280.00",
  "issued_at": "2026-10-20T14:32:05+08:00"
}
```

`amount` 为字符串类型,单位为元,保留两位小数,请勿按浮点数解析。

### 签名校验
值得一提的是,安全永远是第一位的。每个请求都会被附带两个 Header:`X-Fp-Timestamp`(秒级 Unix 时间戳)与 `X-Fp-Signature`。签名算法为 HMAC-SHA256,签名原文为 `timestamp + "\n" + 请求体原文`,密钥为控制台中的 Webhook Secret。您**必须**校验签名,且应拒绝时间戳与当前时间相差超过 300 秒的请求,以防重放攻击。

### 响应与重试
您需要在 5 秒内返回 HTTP 2xx,响应体内容会被忽略。若返回非 2xx 或超时,平台将按 1 分钟、5 分钟、30 分钟、2 小时、6 小时的间隔重试,共重试 5 次;5 次均失败后停止推送,您可通过「查询发票状态」接口主动拉取。

### 幂等处理
同一事件可能被重复投递,这并非 Bug,而是可靠投递的必然代价。请以 `event_id` 作为幂等键做去重,**不要**以 `invoice_no` 去重——同一张发票先开具、后红冲会产生两个不同事件。

愿每一张发票,都能抵达它该去的地方。
