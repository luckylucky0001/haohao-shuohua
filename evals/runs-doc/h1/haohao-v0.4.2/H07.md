### 4. 缓存设计

商品详情页的响应速度会影响转化，所以详情页用多级缓存：进程内 Caffeine 做 L1，Redis 集群做 L2，源是 MySQL。

#### 4.1 缓存层级

| 层级 | 组件 | 缓存内容 | TTL |
|---|---|---|---|
| L1 | 进程内 Caffeine | 商品基础信息、图文详情 | 60 秒 |
| L2 | Redis 集群 | 商品基础信息、图文详情、SKU 规格 | 30 分钟 + 0–300 秒随机抖动 |
| 源 | MySQL `item_detail` 表 | 全量 | — |

Key 格式：`pd:detail:{skuId}:v2`。L1 容量由 `cache.local.max-size=10000` 控制。

价格和库存不进缓存，每次实时读取价格服务和库存服务，以避免出现超卖或价格不一致的情况。

#### 4.2 失效策略

采用 binlog 驱动的失效流程：商品信息变更后，Canal 订阅 `item_detail` 的 binlog，投递到 MQ topic `item-detail-change`，消费者先删除 Redis 中的 key，再广播通知各实例清理 L1。删除失败的消息进入重试队列，最多重试 3 次，仍失败则触发告警。由于 L1 有 60 秒 TTL 兜底，极端情况下数据最多不一致 60 秒。

#### 4.3 命中率目标

- L1 命中率 ≥ 60%（基数为详情页请求总数）；
- L1 + L2 综合命中率 ≥ 98%；
- 回源 MySQL 的 QPS 控制在 2000 以内。

#### 4.4 穿透、击穿与雪崩

- **穿透**：对不存在的 skuId，用布隆过滤器拦截；布隆过滤器误判漏过的请求，在 Redis 中缓存空值，TTL 60 秒。
- **击穿**：热点 key 过期时，同一实例内用 singleflight 合并回源请求；跨实例用 Redis `SET NX` 加锁，锁超时 3 秒，拿不到锁的请求等待 50ms 后重新读缓存。
- **雪崩**：L2 的 TTL 加随机抖动，避免集中过期；Redis 整体不可用时降级为只读 L1，同时对回源 MySQL 限流 2000 QPS，超出部分返回兜底页（只展示标题、主图和“商品信息加载中”）。

热点 key 是否改为逻辑过期 + 异步刷新，待和中间件组对齐后，二期再评估。

这套方案的目的是提升详情页性能，并让大促期间保持稳定，Redis 不可用等极端情况的处理见 4.4。
