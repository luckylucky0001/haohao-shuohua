## 4. 方案对比与选型

车源搜索目前基于 Elasticsearch 7.10，只用 BM25 关键词召回，满足不了用户多样的语义表达需求。

### 4.1 候选方案

- **方案 A**：维持现状，ES 7.10 + BM25 关键词召回；
- **方案 B**：全量迁移到自研向量检索引擎（基于 HNSW）；
- **方案 C**：混合检索，ES 保留关键词召回，同时接入自研向量召回，两路结果用 RRF 融合；
- **方案 D**：将集群升级到 ES 8.x，直接使用其自带的 kNN 检索。

### 4.2 对比数据

离线评测基于 2,000 条人工标注 query：

| 方案 | NDCG@10 | 精确车型类 query Top3 命中率 | 检索 P99 | 机器成本（相对现状） |
|---|---|---|---|---|
| A 现状 | 0.412 | 91% | 85ms | — |
| B 全量向量 | 0.437 | 64% | 60ms | 约 -15% |
| C 混合检索 | 0.468 | 90% | 120ms | 约 +40% |
| D ES 8.x kNN | 未评测 | 未评测 | 未评测 | 未评测 |

### 4.3 分析与结论

方案 B 的整体相关性和延迟都优于现状，成本也更低。但精确车型类 query（如“凯美瑞 2021 款”）占搜索 PV 的 23%，B 在这类 query 上的 Top3 命中率从 91% 降到 64%，这部分流量我们无法接受。

方案 D 需要把集群从 7.10 升级到 8.x，涉及 mapping 和客户端的改造，且 8.x 的 kNN 在我们 3,800 万条车源的规模下表现如何还没有验证过，本期不做评估。

方案 C 的 NDCG@10 最高，为 0.468，车型类 query 命中率与现状基本持平（90%），P99 为 120ms，在 150ms 的延迟预算之内。代价是两套召回都要维护，机器成本约增加 40%。

**结论：选择方案 C（混合检索）。** 二期给向量召回加上 sparse 向量，如果精确车型类 query 的 Top3 命中率 ≥ 88%，再评估是否下掉 ES 关键词召回。精排 / 重排模型的调整不在本次方案范围内。
