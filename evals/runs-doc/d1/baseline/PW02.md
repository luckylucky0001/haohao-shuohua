## 方案选型

### 1. 背景与要求

合同签署超时（7 天）后需自动作废。选型时的约束如下：

- 超时时长为 7 天。
- 业务可接受分钟级精度，作废晚一两分钟没有影响。
- 多实例部署，需避免重复处理。

### 2. 备选方案

#### 方案 A：RocketMQ 延迟消息

- 现状：当前集群为 RocketMQ 4.x，只支持 18 个固定延迟级别，最长 2 小时，不支持自定义。要覆盖 7 天，只能反复投递、逐级拼接，实现别扭。
- 升级路径：升级到 5.x 后支持任意延迟。但集群由中间件组维护，其升级排期在明年 Q1 之后。
- 结论：当前不可行，不选。

#### 方案 B：定时扫表（XXL-JOB）

- 做法：在 contract_task 表上为 expire_at 加索引，XXL-JOB 每分钟扫描一次，每次 limit 500。
- 容量：当前日增合同约 3 万，按峰值测算，该方案够用。
- 精度：分钟级，满足业务要求。
- 并发与幂等：
  - 采用 XXL-JOB 分片广播，按 id 取模分片，避免多实例重复扫描同一批数据。
  - 更新状态时带 version 乐观锁，即使重复执行也是幂等的。

### 3. 对比

| 维度 | 方案 A：延迟消息 | 方案 B：扫表 |
|---|---|---|
| 支持 7 天超时 | 4.x 不支持，需反复投递拼接；5.x 支持 | 支持 |
| 精度 | 不涉及 | 分钟级，业务可接受 |
| 外部依赖 | 依赖中间件组升级 5.x，排期在明年 Q1 之后 | 无 |
| 重复处理 | 不涉及 | 分片 + 乐观锁，幂等 |
| 容量 | 不涉及 | 日增约 3 万，按峰值测算够用 |

### 4. 结论

选择方案 B（定时扫表）。

后续评估条件：当合同日增达到 30 万以上，或 RocketMQ 升级到 5.x 后，重新评估延迟消息方案。

### 5. 待确认事项
